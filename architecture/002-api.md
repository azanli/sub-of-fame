# Sub of Fame - Contracts, Data Types & Redis Schema

Canonical contract companion to `001-overview.md`.

This document owns shared TypeScript types, Redis keys, TTLs, tRPC input/output shapes, backend invariants, and procedure execution flows for the linear progression model. Product overview, UX intent, and build roadmap belong in `001-overview.md`.

---

## Contract Invariants

| Principle             | Decision                                                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Progression           | Linear next-playable rank pointer per subreddit (`rankIndex`), not a seen-set                                                                  |
| Ladder semantics      | `rankIndex` points into the current cached live ladder page, not a permanent canonical post                                                    |
| Played rounds         | Derived from stats counters (`totalSlots / 3`), not from `rankIndex`                                                                           |
| MVP fairness          | Leaderboards are casual social rankings; cached ladder pages may refresh over time                                                             |
| MVP trust boundary    | Pre-submit responses may expose real comment IDs; answer order and scores stay server-held                                                     |
| Puzzle time limit     | Client-calculated from comment bodies on load; not part of `PuzzleNextResponse`                                                                |
| Player skip           | No manual skip-level control; ladder is strictly progressive                                                                                   |
| Ladder pagination     | Cache pages are cursor-linked; a durable `:cursors` chain lets any page be re-fetched directly without re-warming from page 1                  |
| Request work budget   | `puzzle.next` shares one bounded budget across page warming and comment validation; exhaustion returns `unplayable` and retries resume forward |
| Submit correlation    | Server-issued `attemptId` bound to `rankIndex` and frozen attempt owner                                                                        |
| Truth vs presentation | `PuzzleSnapshot` = true rank order; `PuzzleAttempt` = shuffled IDs                                                                             |
| User guess            | Comment IDs placed into each rank slot; not positional indices                                                                                 |
| Logged-out rank       | Client-authoritative; server ignores client rank when logged-in                                                                                |
| Attempt auth state    | Frozen when `puzzle.next` mints the attempt; submit settles against the frozen owner                                                           |
| Skip persistence      | Invalid posts increment progress permanently (logged-in: Redis; logged-out: returned `rankIndex`)                                              |
| Leaderboard credit    | Successful submits only; invalid-post skips never create or advance leaderboard entries                                                        |
| Submit failures       | Explicit `PuzzleSubmitErrorCode` values; rejected submits never update stats or progress                                                       |
| Duplicate submits     | `puzzle:submit-lock:{attemptId}` acquired with Redis `SET NX EX` before scoring or side effects                                                |
| Hive IQ               | Personal logged-in player accuracy: `(correctSlots / totalSlots) × 100`, or `null` when `totalSlots = 0`                                       |
| Hub session           | `activeSubreddit` is ephemeral client state; `init` returns `null` on cold boot                                                                |
| Community host lock   | Non-Hub launches resolve gameplay subreddit from `context.subredditName`, not client selection                                                 |
| Dashboard cards       | `init.dashboardSubreddits` returns fully renderable cards; custom cards do not require client catalog data                                     |

```typescript
export type SubredditOption = {

export const CURATED_SUBREDDITS: SubredditOption[] = [

  {

  },
  // ... top 10 choices

```

Dashboard card shape:

```typescript
type SubredditDisplayMetadata = {
  subreddit: string; // lowercase internal key, e.g. 'askreddit'
  displayName: string; // display casing from curated data or Reddit metadata
  iconUrl: string; // curated icon, Reddit icon, or app fallback icon
};

type SubredditPickerItem = SubredditDisplayMetadata & {
  currentRankIndex: number; // next playable rank; drives reach/progress badge display
  userSubredditHiveIQ: number | null;
  completedRoundCount: number; // derived from sub:total / 3; drives completed puzzle count
  leaderboardRank: number | null;
};
```

For logged-in Hub sessions, the `init` query returns a dashboard cards array that is complete enough to render without a client-side metadata lookup. The server resolves curated cards from `CURATED_SUBREDDITS` and custom cards from Reddit metadata cached under `sub:metadata:{subredditName}`. For logged-out Hub sessions, `init` returns `dashboardSubreddits: null`; the client renders a badgeless curated grid directly from `CURATED_SUBREDDITS`. Logged-in clients may use `CURATED_SUBREDDITS` for static ordering, empty states, or offline fallback copy, but must treat `dashboardSubreddits` as the authoritative render contract when it is present.

Hub dashboard cards are separate from active campaign metrics. On Hub cold boot, `activeSubreddit` is `null`, so the dashboard must be hydrated from global metrics plus per-subreddit cards rather than from a single active-subreddit metric object.

Custom subreddits appear as Hub dashboard cards for logged-in users when they already have persisted data for that subreddit. The server derives the custom dashboard set from the union of:

- custom fields in `user:{userId}:progress`
- custom `sub:{subredditName}:*` counters in `user:{userId}:stats`

This means a custom subreddit requested through the text input appears after the player submits a round or a validation skip advances persisted progress in that subreddit. A validated custom request with no persisted progress or stats does not need to be saved as a dashboard card for MVP.

No separate "create user subreddit" endpoint is required for MVP. `session.selectSubreddit` validates access, resolves display metadata, and warms the ladder cache, but it does not create dashboard membership by itself. If a future version needs saved custom shortcuts before play, add an explicit user-owned set such as `user:{userId}:subreddits` instead of inferring that behavior from validation.

## Launch Context & Subreddit Resolution

Every procedure that touches campaign state derives launch context from Devvit server context before reading request input:

```typescript
type LaunchContext =
  | { surface: 'hub'; hostSubreddit: 'suboffame' }
  | { surface: 'community'; hostSubreddit: string };
```

Resolution rules:

- Normalize `context.subredditName` once per request (`strip r/`, lowercase, trim).
- `surface = 'hub'` only when the normalized host subreddit is `suboffame`.
- Hub gameplay uses a client-selected subreddit. `session.selectSubreddit` validates and warms that selection; `puzzle.next` requires a subreddit because Hub active state is client-ephemeral.
- Community gameplay uses `hostSubreddit` as the effective subreddit. `session.selectSubreddit` is rejected from Community launches. `puzzle.next` may omit `subreddit`; if it includes a subreddit, it must match `hostSubreddit`.
- `puzzle.submit` validates the stored attempt's `subreddit` against the current launch context. In Community launches, `attempt.subreddit` must equal `hostSubreddit`; otherwise the submit is rejected without reveal or mutation.

This keeps the social promise of Community launches: a game post hosted in `r/example` can only play the `r/example` ladder, even if the iframe client sends another subreddit name.

## Redis Schema

### User Progress (logged-in only)

| Key                      | Type | Fields                                                                         |
| ------------------------ | ---- | ------------------------------------------------------------------------------ |
| `user:{userId}:progress` | Hash | `{ [subredditName]: rankIndex }` (integer strings, 1-based next playable rank) |

- Default `rankIndex` for unseen subs: `1`
- Incremented on: invalid-post skips during `puzzle.next`, successful submit (`INCR` by 1)
- Meaning: a player at `rankIndex = 1` is about to play rank 1; after submitting or skipping rank 1, their `rankIndex` becomes `2`.
- Display rule: `rankIndex` is a next-playable reachability pointer. Do not label `rankIndex - 1` as puzzles solved or leaderboard rank because invalid-post skips also advance it.

### Personal User Statistics (logged-in only)

| Key                   | Type | Fields                                                                                       |
| --------------------- | ---- | -------------------------------------------------------------------------------------------- |
| `user:{userId}:stats` | Hash | `global:correct`, `global:total`, `sub:{subredditName}:correct`, `sub:{subredditName}:total` |

- Updated via atomic `HINCRBY` on each submission
- `global:total` and `sub:*:total` increment by 3 per round; `*:correct` increment by score (0–3)
- These are personal counters. `global:*` means "all submitted rounds by this user across all subreddits," not "all players."
- Hive IQ is computed only when the matching `total` counter is greater than `0`; otherwise return `null` for that scope. Do not return `0` for unplayed scopes, because `0` means measured accuracy with no correct slots.
- MVP has no all-player Hive IQ counter. If a future version adds crowd aggregate stats, store them under separate keys such as `stats:global` and `stats:sub:{subredditName}` so product copy can distinguish **Your Hive IQ** from collective crowd accuracy.

### Subreddit Leaderboard (logged-in only)

| Key                           | Type       | Score                                                          | Member   |
| ----------------------------- | ---------- | -------------------------------------------------------------- | -------- |
| `leaderboard:{subredditName}` | Sorted Set | `bestClearedRankIndex` (furthest cleared playable puzzle rank) | `userId` |

- Updated on successful user-owned submit: `ZADD leaderboard:{sub} GT CH {attempt.rankIndex} {userId}`
- A user first appears after a successful submit. Clearing rank 1 writes score `1`; the progress hash separately advances to `rankIndex = 2`.
- `GT` makes the sorted-set score monotonic if future ladder refresh, recovery, admin, or migration paths can produce a lower cleared rank than the user's prior best.
- Invalid-post skips during `puzzle.next` update `user:{userId}:progress` but do not call `ZADD`. This prevents players from gaining leaderboard position from content validation rather than solved gameplay.
- Leaderboard copy should say "best cleared rank" or "furthest cleared playable rank", not "current rank" or "cleared rounds." Display the sorted-set score directly as the cleared rank; do not subtract 1. If the UI needs current next-playable rank, read the progress hash. If it needs puzzles played, derive that separately from stats as `totalSlots / 3`.
- Ties accepted at Redis layer; the user's subreddit Hive IQ breaks ties at display time only

### Subreddit Metadata Cache (custom subreddit display)

| Key                            | Type        | TTL |
| ------------------------------ | ----------- | --- |
| `sub:metadata:{subredditName}` | JSON string | 7d  |

```typescript
type SubredditMetadataCacheEntry = {
  subreddit: string; // lowercase internal key
  displayName: string;
  iconUrl: string; // Reddit icon/communityIcon, or app fallback if unavailable
  fetchedAt: number;
  expiresAt: number;
};
```

Metadata resolution order:

1. If the subreddit exists in `CURATED_SUBREDDITS`, use curated `displayName` and `iconUrl`.
2. Else read `sub:metadata:{subredditName}` if present and unexpired.
3. Else call `reddit.getSubredditByName(name)`, reject inaccessible/quarantined subreddits, normalize `displayName`, and icon fields, then cache the result.
4. If Reddit provides no usable icon, use a stable app fallback icon. Do not omit `iconUrl` from dashboard cards.

This cache is shared metadata, not user progress. It does not imply that a user has selected, played, or saved the subreddit.

### Ladder Cache (shared)

| Key                                  | Type        | TTL |
| ------------------------------------ | ----------- | --- |
| `sub:ladder:{subredditName}:{page}`  | JSON string | 7d  |
| `sub:ladder:{subredditName}:cursors` | JSON string | 30d |

All-time top listings are near-static historical data, so page content is cached for 7d (long enough that a returning daily player almost never triggers a cold re-warm) while the cursor chain that links pages is persisted separately for 30d. The split is deliberate: even after page _content_ expires, the durable cursor chain lets the server re-fetch any single target page directly instead of re-walking the chain from page 1.

Page mapping: page 1 = ranks 1–100, page 2 = 101–200, etc. Reddit top listings are cursor-based, so these pages are not random-access fetches. Page 1 is fetched without a cursor; page N is fetched with the cursor page N-1 reported as its `nextAfter`.

```typescript
type LadderPostSummary = {
  id: string; // t3_...
  title: string;
  hasBody: boolean; // body length >= 50
  isNSFW: boolean;
  isSpoiler: boolean;
  commentCount: number; // Reddit total comments; cheap volume hint, not top-level root proof
};

type LadderCachePage = {
  page: number;
  startsAfter: string | null; // cursor used to fetch this page; null for page 1
  nextAfter: string | null; // cursor for the next page; null means listing exhausted
  posts: LadderPostSummary[];
  fetchedAt: number;
};

// Durable, content-independent index of the cursor chain. Survives page-content
// expiry so deep pages never require re-warming from page 1.
type LadderCursorChain = {
  subreddit: string;
  startsAfter: Record<number, string | null>; // page -> cursor to fetch that page (page 1 = null)
  deepestKnownPage: number; // highest page whose start cursor is known
  terminalPage: number | null; // page where the listing exhausted, if reached
  updatedAt: number;
};
```

Lookup: `page = Math.ceil(rankIndex / 100)`, `offset = (rankIndex - 1) % 100`

Resolving a target page on cache miss:

1. If `sub:ladder:{sub}:{page}` content is present and unexpired, use it.
2. On content miss, consult `sub:ladder:{sub}:cursors`:
   - If `startsAfter[page]` is known, fetch that one page directly with `getTopPosts({ subredditName, time: 'all', limit: 100, after: startsAfter[page] })` (page 1 uses no `after`). This is a single round-trip regardless of depth.
   - If `startsAfter[page]` is unknown, warm forward only from `deepestKnownPage` (never from page 1 when a deeper cursor exists), fetching each intermediate page once to extend the chain until `page` is reached or the listing exhausts.
3. Every `getTopPosts` consumes the shared `puzzle.next` work budget (see [Serverless Work Budget](#serverless-work-budget-puzzlenext)). If the budget is exhausted before the target page is reached, return `unplayable` with the current `rankIndex`; the pages and cursors already persisted let the next request resume forward instead of restarting.
4. Persist each fetched `LadderCachePage` (7d) and update `LadderCursorChain` (30d) with every newly learned `startsAfter[page + 1] = nextAfter` and a raised `deepestKnownPage`.
5. If a page returns fewer than 100 posts or `nextAfter === null`, record `terminalPage` and treat the ladder as exhausted after that page's final post.

If a stored cursor has gone stale (Reddit returns an unexpected or empty page because the underlying post moved or was removed), the warm routine falls back to extending forward from the deepest page that still resolves, spending budget rather than failing hard. For hackathon scope this remains a live cursor index, not a canonical archive.

MVP fairness note: this is a live ladder cache, not a stable canonical ladder. If a page expires and Reddit's all-time ranking has changed, later players may see different source posts at the same `rankIndex`. Leaderboards should be presented as casual progress rankings rather than strict competitive standings.

Title validation: `title.length >= 10` OR `hasBody === true`.

Comment-count prefilter: `commentCount >= 10` is only a cheap way to reject obviously low-discussion posts before paying for comment extraction. Reddit's public comment count includes replies and unavailable comments, so it must not be treated as evidence that the post has three valid top-level roots. The authoritative playability check remains the `depth: 1` top-comment extraction contract below. If the extraction cannot produce three valid, distinct-score roots from the initial top-level response, the post is invalid and the skip loop advances.

### Puzzle Snapshot (shared, comment truth)

| Key                              | Type        | TTL |
| -------------------------------- | ----------- | --- |
| `puzzle:snapshot:{sourcePostId}` | JSON string | 7d  |

```typescript
type PuzzleCommentSnapshot = {
  id: string; // t1_...
  body: string;
  score: number; // frozen upvotes at snapshot time
  createdAt: number;
};

type PuzzleSnapshot = {
  sourcePostId: string;
  post: { title: string; body?: string; imageUrl?: string };
  comments: [
    PuzzleCommentSnapshot,
    PuzzleCommentSnapshot,
    PuzzleCommentSnapshot,
  ];
  // index 0 = #1 most upvotes (true rank); never scrambled
  createdAt: number;
  expiresAt: number;
};
```

Created on first valid post after comment extraction (`getComments({ sort: 'top', depth: 1 })` → validate top-level roots → first 3 distinct-score roots).

### Comment Validation Contract

Comment extraction is intentionally strict because the game asks players to infer public popularity. If the backend cannot produce three unambiguous, meaningful top-level roots, the source post is invalid and `puzzle.next` advances to the next ladder item.

Candidate fetch:

- Request top-level comments only: `getComments({ sort: 'top', depth: 1 })`.
- Ignore replies entirely for MVP.
- Evaluate enough returned roots to find three valid comments, but do not perform deep pagination for hackathon scope. If the initial top-comment response cannot produce three playable roots, treat the post as invalid.

A comment root is invalid when any of these are true:

- The comment is deleted, removed, collapsed into an unavailable placeholder, or has a body equal to `[deleted]` or `[removed]`.
- The author is `AutoModerator`.
- The comment is stickied, distinguished by a moderator/admin, or otherwise system/moderation-oriented rather than ordinary user content.
- The normalized body is empty or has fewer than 20 visible characters after trimming and whitespace collapse.
- The score is missing, hidden, non-numeric, or otherwise unavailable at snapshot time.

Selection and tie handling:

- Normalize candidate bodies before validation and before storing the snapshot.
- Sort valid roots by score descending.
- Select the first three roots only if their scores are all distinct.
- If any selected comments have tied scores, reject the post instead of applying a hidden tie-breaker.
- Ties outside the selected three do not affect the puzzle.

### Puzzle Attempt (ephemeral, per round)

| Key                              | Type        | TTL |
| -------------------------------- | ----------- | --- |
| `puzzle:attempt:{attemptId}`     | JSON string | ~1h |
| `puzzle:submit-lock:{attemptId}` | String lock | 1h  |

```typescript
type PuzzleAttemptOwner = { kind: 'user'; userId: string } | { kind: 'guest' };

type PuzzleAttempt = {
  attemptId: string;
  sourcePostId: string;
  subreddit: string;
  rankIndex: number; // rank being played; equals currentRankIndex when attempt is minted
  owner: PuzzleAttemptOwner; // frozen at puzzle.next mint time
  commentOrder: [string, string, string]; // shuffled presentation order
  submitted: boolean;
  createdAt: number;
  expiresAt: number;
};
```

Attempt ownership is determined only when `puzzle.next` creates the attempt:

- Logged-in `puzzle.next` -> `{ kind: 'user', userId }`
- Logged-out `puzzle.next` -> `{ kind: 'guest' }`

Submitting a guest attempt while currently logged in does not attach that round to the user account. It still scores and reveals as a guest round, returns `userHiveIQ: null`, and returns `nextRankIndex: attempt.rankIndex + 1` for guest progression only. If the client continues in logged-in mode, the next `puzzle.next` call uses Redis progress and ignores that guest rank. This avoids crediting an account for a round that was selected with client-authoritative logged-out progress.

Submitting a user attempt requires the same current Devvit user. If the player logs out, switches accounts, or loses user context before submit, the backend returns `WRONG_USER` without reveal or mutation. The client should then refresh game state and request the authoritative next puzzle.

### Puzzle Flow

```typescript
export type PuzzleNextRequest = {
  subreddit?: string; // required on Hub; optional in Community because host context is authoritative
  rankIndex?: number; // logged-out next playable rank only; ignored when logged-in
};

export type PuzzleNextResponse =
  | {
      status: 'ready';
      attemptId: string;
      rankIndex: number; // rank being played
      post: { title: string; body?: string };
      comments: Array<{ id: string; body: string }>; // shuffled, no scores
    }
  | {
      status: 'exhausted';
      rankIndex: number; // next playable rank after any skips
      message: string;
    }
  | {
      status: 'unplayable';
      rankIndex: number; // rank to retry, or next playable rank after bounded skips
      message: string;
    }
  | {
      status: 'error';
      code:
        | 'SUBREDDIT_REQUIRED'
        | 'SUBREDDIT_UNAVAILABLE'
        | 'HOST_SUBREDDIT_LOCKED';
      message: string;
    };

// MVP identity/trust note:
// comments[].id is the real Reddit comment ID, not an opaque client-only ID.
// A motivated player could use it to look up source comments externally and infer scores.
// For hackathon scope, that casual trust tradeoff is acceptable; the server still
// withholds true answer order, frozen scores, and scoring result until submit.

export type PuzzleSubmitRequest = {
  attemptId: string;
  slots: [string, string, string]; // comment IDs placed into rank slots 1/2/3; must be a permutation of attempt.commentOrder
};

export type PuzzleSubmitSuccess = {
  status: 'submitted';
  score: number; // 0–3
  slots: Array<{
    commentId: string;
    body: string;
    score: number;
    correct: boolean;
  }>;
  userHiveIQ: UserActiveSubredditMetrics | null; // null for guest attempts
  nextRankIndex: number; // next playable rank after this submit; syncs guest or user progression
};

export type PuzzleSubmitErrorCode =
  | 'ATTEMPT_EXPIRED'
  | 'ATTEMPT_ALREADY_SUBMITTED'
  | 'INVALID_SLOT_PERMUTATION'
  | 'HOST_SUBREDDIT_LOCKED'
  | 'WRONG_USER'
  | 'SNAPSHOT_MISSING'
  | 'STALE_PROGRESS';

export type PuzzleSubmitError = {
  status: 'error';
  code: PuzzleSubmitErrorCode;
  message: string;
  nextAction: 'request_next_puzzle' | 'resubmit_valid_slots' | 'refresh_game';
  currentRankIndex?: number; // present when the server can report the authoritative rank
};

export type PuzzleSubmitResponse = PuzzleSubmitSuccess | PuzzleSubmitError;
```

Submit error meanings:

| Code                        | Trigger                                                                                                                         | Client behavior                                                                                            |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `ATTEMPT_EXPIRED`           | `puzzle:attempt:{attemptId}` is missing, usually because its TTL elapsed                                                        | Discard local attempt and request the next puzzle                                                          |
| `ATTEMPT_ALREADY_SUBMITTED` | Attempt exists with `submitted: true`                                                                                           | Treat the round as closed and request the next puzzle                                                      |
| `INVALID_SLOT_PERMUTATION`  | `slots` does not contain exactly the three comment IDs issued in `attempt.commentOrder` (wrong IDs, duplicates, or wrong count) | Keep the same puzzle visible, display the correct order, and let the user choose to view thread or advance |
| `HOST_SUBREDDIT_LOCKED`     | Community launch attempts to submit a round whose stored subreddit does not match the host subreddit                            | Refresh game state and request the host community's puzzle                                                 |
| `WRONG_USER`                | User-owned attempt does not match the current Devvit user, or the current user is absent                                        | Refresh game state; do not reveal or score                                                                 |
| `SNAPSHOT_MISSING`          | Attempt exists, but `puzzle:snapshot:{sourcePostId}` is missing                                                                 | Discard local attempt and request the next puzzle                                                          |
| `STALE_PROGRESS`            | User-owned attempt's current Redis progress for the subreddit no longer equals `attempt.rankIndex`                              | Discard local attempt and request the authoritative next puzzle                                            |

Rejected submits are non-mutating: they must not mark the attempt submitted, increment stats, increment progress, or update the leaderboard.

Atomic duplicate-submit guard:

- `puzzle:attempt:{attemptId}` keeps `submitted` for durable attempt state and readable error handling.
- Redis `SET puzzle:submit-lock:{attemptId} 1 NX EX 3600` is the race-proof submit gate.
- The server acquires the submit lock only after all non-mutating validation has passed: valid slot permutation, attempt exists, launch context matches, owner matches, user progress is not stale, and the snapshot exists.
- If `SET NX` fails, return `ATTEMPT_ALREADY_SUBMITTED` without scoring, revealing, incrementing stats, advancing progress, or updating the leaderboard.
- Only the request that acquires the lock may score the guess, mark the attempt JSON as `submitted: true`, advance guest/user progress, update stats, update the leaderboard, and return the reveal payload.
- The lock TTL should match the attempt TTL for MVP (`3600` seconds). The attempt's `submitted` field remains the canonical "round is closed" marker after the winning request completes; the lock exists to make the close transition atomic under simultaneous requests.

## Serverless Work Budget (`puzzle.next`)

`puzzle.next` is the only procedure that can chain multiple Reddit round-trips in a single request: ladder page warming (`getTopPosts`) and comment validation (`getComments`). To prove the procedure stays under the Devvit serverless execution limit, both kinds of work draw from **one shared budget** rather than two independent caps that silently compete for the same wall-clock.

```typescript
type NextWorkBudget = {
  redditCallsRemaining: number; // shared across getTopPosts + getComments
  softDeadlineAt: number; // Date.now() backstop; stop starting new expensive work past it
  itemsCheckedRemaining: number; // logical skip cap, subordinate to redditCallsRemaining
};
```

MVP constants (tunable values chosen to stay under the platform limit; they are not platform constants themselves):

- `MAX_REDDIT_CALLS = 12` — combined ceiling for page warms plus comment fetches in one request.
- `MAX_ITEMS_CHECKED = 20` — max ladder items inspected before giving up this request.
- `SOFT_DEADLINE_MS` — chosen to keep total wall-clock safely under the serverless execution limit.

Rules:

- Every `getTopPosts` (page warm) and every `getComments` (validation) decrements `redditCallsRemaining` by 1.
- Before starting any expensive call, the loop checks `redditCallsRemaining > 0` **and** `Date.now() < softDeadlineAt`; if either fails, it stops and returns `{ status: 'unplayable', rankIndex }`.
- `itemsCheckedRemaining` bounds how many ladder entries are inspected; it cannot, on its own, authorize more Reddit calls than `redditCallsRemaining` permits.
- The cheap `LadderPostSummary` fast-filter (NSFW, spoiler, title/body, `commentCount`) is free and does not consume the budget; only Reddit round-trips do.
- **Forward-progress guarantee:** warmed pages (`sub:ladder:{sub}:{page}`), the durable cursor chain (`sub:ladder:{sub}:cursors`), and invalid-post skip increments to `user:{userId}:progress` all persist. Each retry therefore resumes with strictly less remaining work and converges to `ready` or `exhausted`, so an `unplayable` result is always a continuation point, never a dead end.

## tRPC Procedure Execution Flows

Hono hosts the server runtime, but these contracts are implemented as tRPC procedures rather than standalone REST routes.

### `init` query

1. Normalize `context.subredditName` and derive `LaunchContext`.
2. If logged-out → `userGlobalHiveIQ: null`, `dashboardSubreddits: null`, `activeSubredditMetrics: null`. In logged-out Hub sessions, the client displays the static curated grid from `CURATED_SUBREDDITS` without user-specific badges.
3. If logged-in → parallel fetch `user:{userId}:progress` and `user:{userId}:stats`.
4. Set `activeSubreddit`: Community → `hostSubreddit`; Hub → `null`.
5. Compute `UserGlobalHiveIQMetrics` from that user's global stats counters; set `userGlobalHiveIQ: null` when `global:total = 0`.
6. If Hub → build dashboard subreddit set:
   - include every `CURATED_SUBREDDITS` item in curated order
   - include custom subreddit names discovered from progress hash fields and `sub:{subredditName}:*` stats fields
   - exclude duplicates after normalization; sort by subreddits with the highest rank index
7. Resolve display metadata for every dashboard subreddit. Curated metadata comes from `CURATED_SUBREDDITS`; custom metadata comes from `sub:metadata:{subredditName}` or a fresh `reddit.getSubredditByName` lookup.
8. Fetch leaderboard ranks for the final dashboard set.
9. Return `dashboardSubreddits` with display metadata, progress, nullable user subreddit Hive IQ, completed round count, and leaderboard rank per dashboard subreddit.
10. If Community → return `activeSubredditMetrics` for `hostSubreddit` with `userSubredditHiveIQ: null` when `sub:{hostSubreddit}:total = 0`; `dashboardSubreddits` remains `null`.

### `session.selectSubreddit` mutation (Hub only)

1. Derive `LaunchContext`; if Community → return `HOST_SUBREDDIT_LOCKED`.
2. Sanitize input (strip `r/`, lowercase, trim).
3. Match against `CURATED_SUBREDDITS` → proceed if found.
4. Else → resolve and cache custom display metadata via `getSubredditByName`; reject if inaccessible/quarantined.
5. Lazy-warm `sub:ladder:{sub}:1` if missing. This creates the first cursor boundary for later ranks.
6. Return `{ activeSubreddit, currentRankIndex, subredditMetadata }` from progress hash (default `1`). This does not create dashboard membership by itself.

### `puzzle.next` mutation

1. Derive `LaunchContext` and resolve the effective subreddit:
   - Hub → require `request.subreddit`; sanitize and validate it as a curated or accessible custom subreddit.
   - Community → use `hostSubreddit`; if `request.subreddit` is present and does not normalize to `hostSubreddit`, return `HOST_SUBREDDIT_LOCKED`.
2. Resolve `rankIndex`: logged-in → Redis progress for the effective subreddit; logged-out → request body value (default `1`).
3. Initialize the shared `NextWorkBudget` (`redditCallsRemaining = MAX_REDDIT_CALLS`, `softDeadlineAt = Date.now() + SOFT_DEADLINE_MS`, `itemsCheckedRemaining = MAX_ITEMS_CHECKED`). Page warming and comment validation both draw from this one budget (see [Serverless Work Budget](#serverless-work-budget-puzzlenext)).
4. **Evaluation loop** (bounded by the shared budget, not an independent iteration count):
   - Before any expensive Reddit call, check the budget: if `redditCallsRemaining <= 0` or `Date.now() >= softDeadlineAt`, return `{ status: 'unplayable', rankIndex }` with the current next-playable rank.
   - Compute `page` and `offset` from `rankIndex`.
   - Ensure `sub:ladder:{sub}:{page}` content exists using the durable cursor chain (fetch the target page directly when `startsAfter[page]` is known; otherwise warm forward from `deepestKnownPage`, never from page 1). Each `getTopPosts` decrements `redditCallsRemaining`.
   - Read post from `sub:ladder:{sub}:{page}` at offset.
   - If no post exists and the page is terminal (`nextAfter === null` or fewer than 100 posts) → return `{ status: 'exhausted' }`.
   - Fast-filter via `LadderPostSummary` (NSFW, spoiler, title/body, `commentCount >= 10` discussion-volume hint). This filter is free and does not consume the budget.
   - If invalid → increment progress pointer (Redis if logged-in), decrement `itemsCheckedRemaining`; if `itemsCheckedRemaining <= 0` return `{ status: 'unplayable', rankIndex }`; otherwise continue.
   - Load or create `PuzzleSnapshot` using the authoritative top-level comment validation contract. The `getComments` call decrements the same `redditCallsRemaining`; if the budget does not permit it, return `{ status: 'unplayable', rankIndex }` before calling.
   - If comment extraction fails → treat as invalid using the same skip cap (advance progress, decrement `itemsCheckedRemaining`).
5. Mint `puzzle:attempt:{attemptId}` with the effective subreddit, frozen `owner`, and shuffled `commentOrder`.
6. Return `{ status: 'ready', attemptId, rankIndex, post, comments }` (no scores).

Skip/leaderboard rule: the evaluation loop may permanently advance logged-in progress across invalid posts before a playable puzzle is found, but those skip increments are not leaderboard events. A leaderboard entry is written only after a successful user-owned `puzzle.submit`, using the attempt's `rankIndex` as the cleared playable rank.

### `puzzle.submit` mutation

1. Validate `slots` contains exactly the three comment IDs in `attempt.commentOrder` (each used exactly once); otherwise return `INVALID_SLOT_PERMUTATION`. Note: this validation requires the attempt to be loaded first (step 2); a lightweight structural check — three distinct non-empty strings — may be applied before loading as an early exit.
2. Load `PuzzleAttempt` by `attemptId`; if missing return `ATTEMPT_EXPIRED`.
3. If `attempt.submitted === true`, return `ATTEMPT_ALREADY_SUBMITTED`.
4. Derive `LaunchContext`; if Community and `attempt.subreddit !== hostSubreddit`, return `HOST_SUBREDDIT_LOCKED` without reveal or mutation.
5. If `attempt.owner.kind === 'user'`, require the current Devvit user to match `attempt.owner.userId`; otherwise return `WRONG_USER`.
6. For user-owned attempts, read the authoritative progress for `attempt.subreddit`; if it does not equal `attempt.rankIndex`, return `STALE_PROGRESS` with `currentRankIndex`.
7. Load `PuzzleSnapshot` by `sourcePostId`; if missing return `SNAPSHOT_MISSING`.
8. Acquire `puzzle:submit-lock:{attemptId}` with `SET ... NX EX 3600`; if the lock already exists, return `ATTEMPT_ALREADY_SUBMITTED`.
9. Score: for each slot `i`, compare `slots[i]` directly against `snapshot.comments[i].id` → 1 point per match. No index indirection is required; the submitted IDs are compared directly to the true rank order.
10. Persist the attempt JSON with `submitted: true`.
11. If `attempt.owner.kind === 'user'`:

- `HINCRBY` stats counters.
- `HINCR` progress for `attempt.subreddit`, producing `nextRankIndex`.
- `ZADD leaderboard:{sub} GT CH {attempt.rankIndex} {userId}`.

12. If `attempt.owner.kind === 'guest'`, compute `nextRankIndex = attempt.rankIndex + 1` without updating Redis, stats, or leaderboards.
13. Return reveal payload with frozen scores. Include updated personal Hive IQ only for user-owned attempts.

## Scoring Reference

```
slotScore = count of i where slots[i] === snapshot.comments[i].id
userHiveIQ = totalSlots === 0 ? null : (correctSlots / totalSlots) * 100
```

Submit validates `slots` is a permutation of `attempt.commentOrder` (all three comment IDs from the attempt, each used exactly once). This removes any positional coupling between the response array and scoring: the server may return `PuzzleNextResponse.comments` in any order for rendering, and the client ranks cards via Tap-to-Rank, because what is submitted are comment IDs — not presentation indices.

## Client Gameplay Contract

Canonical UX and timer behavior live in `004-puzzle-time-clock.md`. This section records API-adjacent client obligations that affect submit handling.

### Tap-to-Rank (replaces drag-and-drop)

- After start, comments render inside a modal overlay on the source post.
- Comments appear in a fixed vertical stack in shuffled presentation order.
- The player assigns ranks 1→3 by tapping unselected cards sequentially.
- Tapping an already selected card clears that card's rank and every rank after it; lower ranks remain (e.g. with `①` and `②` set, tapping the `②` card clears only `②`).
- When all three ranks are assigned, the client auto-invokes `puzzle.submit` (or enables **Submit Order** immediately before submit—auto-submit is preferred).

### Start Puzzle gate

- On `ready`, show post title/body (and optional image) only; hide comments. Post body is always fully shown pre-start and is not collapsible.
- **Start Puzzle** opens the comments modal over the post, starts the client timer, and begins Tap-to-Rank. No countdown before this action.

### Client-side timer

- Compute allotted seconds from the three comment `body` strings when the puzzle loads; do not expect a timer field from the server.
- Formula: `clamp(Math.ceil(wordCount / 2.5) + 15, 30, 120)` where `wordCount = Math.ceil(combinedBodyLength / 5)`.

### Timeout force-submit

When the countdown reaches zero:

| Client selection state    | Submit behavior                                                                                                                                                |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Three ranks assigned      | Submit that permutation immediately.                                                                                                                           |
| One or two ranks assigned | Submit assigned IDs into their rank slots; fill remaining slots with unassigned comment IDs in stable presentation-array order to produce a valid permutation. |
| No ranks assigned         | Submit an empty guess (score `0`). Implementation must complete the submit lifecycle without trapping the player—see timeout submit note below.                |

### Timeout empty submit (implementation note)

`PuzzleSubmitRequest.slots` today requires a full permutation of `attempt.commentOrder`. A timeout with zero taps is product-defined as a failed round (score `0`, progress advances). When implementing, either extend `puzzle.submit` to accept an explicit timeout/empty payload or map empty timeout to a score-0 path that still closes the attempt and returns reveal with `score: 0`. Do not leave the player stuck behind `INVALID_SLOT_PERMUTATION` after timeout.
